    Convenciones¶

    Código¶

    Elemento Convención Ejemplo
    Idioma del código Nombres de negocio en español, términos técnicos en inglés class SolicitudCompra, service.py
    Python snake_case para funciones y variables, PascalCase para clases aprobar_solicitud()
    TypeScript camelCase para variables, PascalCase para componentes SolicitudForm
    Formato Ruff (Python), Prettier (TypeScript)

    Base de datos¶

    Elemento Convención Ejemplo
    Tablas snake_case, prefijo del módulo cmp_orden_compra
    Llave primaria id UUID
    Auditoría creado_por, creado_en, actualizado_por, actualizado_en en toda tabla
    Montos NUMERIC(18,4) + código de moneda ISO 4217 monto, moneda = 'PEN'
    Fechas y horas UTC en BD, zona horaria del usuario en pantalla

    Prefijos de tablas: seg seguridad, mae maestros, sol solicitudes, cmp compras, inv inventarios, cxp cuentas por pagar, cnt contabilidad, cxc cuentas por cobrar.

    API¶

    • Ruta base versionada: /api/v1/<modulo>/<recurso>.
    • Recursos en plural y en minúsculas: /api/v1/compras/ordenes.
    • Errores con formato único: {"codigo": "...", "mensaje": "..."}.
    • Toda ruta declara el permiso que exige.

    Pantallas (frontend)¶

    • Menú: cada módulo se registra en MENU de frontend/src/App.tsx con grupo: "negocio" (módulos de operación, arriba) o grupo: "administracion" (configuración, plegado al pie).
    • Botones que guardan: usar BotonAccion de componentes.tsx con ocupado mientras se ejecuta; nunca un <button disabled> para indicar que algo está en proceso.
    • Confirmación: tras toda acción exitosa llamar avisar("…") de useAvisos(); en formularios que no se cierran, además useConfirmacion() para mostrar ✓ Guardado en el botón.
    • Gris = no permitido: el estado deshabilitado se reserva para acciones sin permiso o no aplicables.

    Documentos operativos¶

    Todo documento operativo (solicitud, orden de compra, recepción, factura…) cumple ADR-005:

    • Sus tablas de cabecera, línea y distribución heredan ConAtributos (app/core/atributos.py) y su migración agrega *columnas_atributos().
    • El documento se registra en DOCUMENTOS y, si genera otro, en FLUJOS.
    • El servicio valida con seguridad.atributos.validar_valores al guardar, propone valores_por_defecto al crear y usa copiar_valores al generar el documento siguiente.
    • La pantalla usa <CamposAtributos documento nivel valores onCambio /> en cada nivel.

    Comunicación entre módulos¶

    • Un módulo llama a otro solo por su service.py.
    • Cuando un módulo debe reaccionar a algo de otro sin acoplarlos, se usa app/core/eventos.py: el publicador llama emitir("empresa_creada", …) y el interesado se registra con @suscribir("empresa_creada"). Ejemplo: Contabilidad carga el plan de cuentas al crear una empresa sin que Maestros conozca a Contabilidad.
    • Lo propio de cada país (identificación fiscal, plantilla contable, impuestos) vive en app/localizacion/<país>.

    Git¶

    • Rama principal main; trabajo en ramas semana-N/tarea.
    • Mensajes de commit: modulo: qué cambió (ej. seguridad: alta de roles).

    Roles¶

    • Todo módulo define en catalogo.py un rol estándar por tipo que aplique: administrador, configuración, operativo y consulta.
    • Código de todo rol: ERP_<ABREVIATURA>_<FUNCIÓN> en mayúsculas (ej. ERP_COM_ADMINISTRADOR, ERP_COM_ANALISTA). La abreviatura de 3 letras se define en catalogo.MODULOS.
    • Nombre del rol en español, en singular y por puesto de trabajo.
    • Los roles propios del cliente siguen la misma nomenclatura y normalmente se crean duplicando uno estándar.
    • Permisos de un rol de consulta: solo acciones ver.
